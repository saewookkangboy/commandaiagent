# Agentic AI 시대 마케터의 기술 대응: Harness·Loop·Graph·Jev Engineering 실무 가이드

마케터가 Agentic AI에 대응하는 방법은 새로운 모델을 모두 따라가는 것이 아닙니다. **업무의 규칙을 고정하고, 실행 상태를 기록하며, 반복과 승인 경로를 설계한 뒤, 필요한 판단만 모델에 맡기는 것**입니다. Harness는 운영 환경, Loop는 실행과 평가의 반복, Graph는 상태와 업무 경로, Jev는 일부 판단을 담당하는 결정 모델로 이해하면 내 업무의 어디를 바꿔야 할지 보입니다.

이 글은 **2026년 10월 17일 확인한 공개 자료**와 제공된 기술 콘텐츠를 바탕으로 정리한 실무 응용 가이드입니다. 아래 캠페인과 코드의 수치는 설명을 위한 예시이며, 특정 제품 도입의 성과를 보장하지 않습니다. 기존 [Jev Engineering 입문](/blog/jev-engineering-guide)이 모델의 역할을 설명했다면, 여기서는 마케터가 개발자와 무엇을 합의하고 어떤 업무부터 적용할지에 집중합니다.

## 1. 2026년 10월의 변화는 모델 교체보다 업무 구조의 변화다

2026년 2월 OpenAI의 Harness Engineering 글은 Agent가 작업할 환경, 접근 가능한 지식, 구조적 제약과 피드백 루프를 설계하는 일을 강조했습니다. 해당 사례는 소프트웨어 개발 실험입니다. 마케팅 전체의 생산성이 같은 비율로 개선된다는 근거는 아닙니다. 다만 팀 규칙이 사람의 머릿속에만 있으면 Agent가 일관되게 따르기 어렵다는 점은 실무에 적용할 수 있습니다. [1]

2026년 9월 25일 LangChain의 Jev·LangGraph 글은 **코드가 업무 흐름을 유지하고, 모델은 좁은 의미 판단을 맡는 구성**을 소개했습니다. 10월 1일의 모델 라우터 글도 업무의 종류와 문맥, 실제 결과 평가를 먼저 분석한 뒤 모델을 선택했습니다. 마케터의 대응 순서 역시 “가장 비싼 모델 연결”이 아니라 “우리 업무에서 무엇이 판단이고 무엇이 실행인가”를 분리하는 쪽이어야 합니다. [2] [3]

Harness → Loop → Graph → Jev는 이 글의 **이해·도입 순서**입니다. 업계가 합의한 기술 연대기나 이전 기술을 반드시 폐기해야 하는 네 단계는 아닙니다. Harness 안에서 Loop가 돌고, Graph가 그 경로를 표현하며, Jev가 일부 분기 판단에 들어갈 수 있습니다. 기존 LLM이나 규칙 기반 자동화로 충분하면 Jev를 추가하지 않아도 됩니다.

Agentic AI 역시 모든 제품에서 같은 기능을 뜻하지 않습니다. 이 글에서는 모델이 도구와 실행 결과를 보고 다음 행동을 선택하는 시스템을 중심으로 다룹니다. 정해진 경로를 따르는 워크플로와 더 자율적인 Agent를 구분하되, 실제 업무에서는 두 방식을 조합할 수 있습니다. [4]

## 2. Harness: 프롬프트 밖에 운영 규칙을 만들기

Harness는 모델이 도구를 호출하고 결과를 확인하는 실행 환경과 제어 장치를 뜻합니다. 프롬프트, 도구 인터페이스, 권한, 상태 저장, 검증과 로그가 함께 작동해야 합니다. 지시문에 “외부 발행 금지”를 적어놓고 동일 Agent에 자유로운 발행 권한을 주는 것은 충분한 통제가 아닙니다. 도구의 권한과 서버의 정책도 같은 제약을 적용해야 합니다. [1] [4]

마케터는 먼저 한 업무의 **단일 기준 원본**을 정합니다. B2B 캠페인이라면 승인된 제품 설명, 고객군, 가격, 금지 표현, CTA 목적과 성과 지표 정의입니다. 문서마다 다른 가격이나 전환 정의를 넣지 말고 버전과 적용일을 관리합니다. 짧은 업무 지시서는 필요한 문서의 위치를 안내하고, 모든 자료를 한 프롬프트에 반복해서 넣지 않습니다. [1]

제공된 Harness 구축 사례에서 응용할 만한 관점도 같습니다. 역할을 나누기 전에 지시, 상태, 검증, 범위와 작업의 시작·종료 기준을 정하는 것입니다. CRM 세그먼트 기준이나 UTM 규칙처럼 정확히 처리해야 하는 항목은 코드와 스키마로 검사하고, 모델에는 해석이나 문장 작성처럼 필요한 부분만 맡깁니다.

**개발자에게 전달할 첫 합의문**은 다음처럼 구체적이어야 합니다.

```text
업무: 승인된 제품 자료로 B2B 콘텐츠 캠페인 초안 만들기
입력 원본: product_brief_v3, audience_rules_v2, measurement_spec_v1
허용 도구: 지정 자료 읽기, 집계 지표 조회, 초안 저장
금지 작업: 광고 예산 변경, 이메일 발송, 원본 고객 목록 내보내기
산출물: 메시지 가설, 채널별 초안, 근거 목록, 수정 필요 항목
완료: 검수 통과 초안을 사람이 확인할 수 있는 위치에 저장
미완료: 자료 누락·권한 오류·근거 충돌이면 해당 사유와 함께 중단
외부 실행: 이 업무의 초안 생성 권한에 포함하지 않음
```

이 예시는 도구를 실제 연결하는 설정 파일이 아닙니다. 각 항목이 접근 제어와 검증 코드에 어떻게 대응하는지 개발자와 확인해야 합니다. 자료 준비가 필요하면 [R-G-C-T-O-R 업무 지시서 워크시트](/resources/rgctor-worksheet)를 먼저 사용해도 됩니다.

## 3. Loop: 더 많이 반복하기보다 멈출 조건을 설계하기

Agent Loop는 대략 “다음 행동 선택 → 도구 실행 → 결과 관찰 → 평가 → 다음 행동 또는 종료”로 이해할 수 있습니다. 마케팅 전략에서 말하는 지속적 학습의 Loop와 관련은 있지만, 여기서는 **프로그램의 실행·재시도·종료 구조**를 뜻합니다.

콘텐츠 초안에 근거 없는 가격이 있으면 검수가 이유를 반환하고 작성 단계가 해당 부분만 수정합니다. 이미 통과한 타깃 분석까지 다시 생성할 필요는 없습니다. 반면 제품 자료에 가격이 없으면 같은 모델을 반복 호출해도 사실을 얻을 수 없습니다. 이 경우는 `needs_input`으로 멈추고 자료 담당자에게 확인해야 합니다.

재시도와 재생성도 구분해야 합니다. 일시적인 조회 실패는 정해진 횟수 안에서 기다렸다가 다시 시도할 수 있습니다. 인증 실패는 권한 복구가 필요하며, 이미 이메일이 발송됐는지 모르는 상황은 중복 여부 확인이 먼저입니다. “실패하면 처음부터 다시”는 중복 발송이나 반복 비용을 만들 수 있습니다.

실무에서는 완료, 자료 대기, 사람 검토, 실패를 서로 다른 상태로 남깁니다. 예를 들어 `passed`, `needs_input`, `needs_review`, `failed`를 구분하고, 반복 횟수·경과 시간·비용 한도를 함께 둡니다. 한도에 도달하면 성공으로 표시하지 말고 마지막 정상 상태와 중단 이유를 반환합니다.

장기 실행에 관한 Anthropic의 사례도 완료 기준을 따로 기록하고, 한 번에 작은 작업을 진행하며, 다음 실행이 읽을 수 있는 진행 기록을 남기는 방식을 제시했습니다. 중요한 것은 모델이 “끝났다”고 말했는지가 아니라 **합의한 산출물과 검증 결과가 남았는지**입니다. [5]

## 4. Graph: Agent 숫자가 아니라 업무의 인계 조건을 설계하기

Graph는 업무를 노드와 경로로 표현합니다. 노드는 모델 호출뿐 아니라 데이터 계산, 도구 실행, 검수, 사람 승인일 수 있습니다. 상태는 각 노드가 읽거나 갱신하는 정보이고, 경로는 다음에 실행할 노드를 정합니다. Graph를 쓴다고 반드시 다중 Agent가 필요한 것은 아닙니다. [2]

B2B 캠페인의 경로를 다음처럼 시작할 수 있습니다.

```text
자료 확인 → 메시지 가설 → 채널별 초안 → 검수 → 사람 승인 → 발행 단계
자료 누락 → 자료 요청 후 대기
근거 오류 → 해당 초안만 수정
민감 표현·판단 불확실 → 사람 검토
승인 이후 초안 변경 → 기존 승인 무효화 후 다시 승인
```

마케터가 정해야 할 것은 노드의 이름보다 **인계 계약**입니다. 분석 단계가 무엇을 내놓아야 작성 단계가 시작할 수 있는지, 검수 실패가 어느 단계로 돌아가는지, 발행 담당자가 어떤 버전의 승인을 확인하는지 정합니다.

```json
{
  "campaign_id": "campaign_demo",
  "brief_version": "v3",
  "draft_version": "v2",
  "status": "needs_review",
  "evidence_refs": ["product_brief_v3"],
  "review_failures": [],
  "approval": null
}
```

이 상태 예시에는 고객 원문이나 인증 키가 없습니다. 실제 저장소에는 접근 권한과 보유 기간을 적용해야 합니다. 고객별 정보가 필요하다면 전체 리스트를 모든 노드에 전달하지 말고, 해당 판단에 필요한 최소 정보만 전달합니다.

LangGraph의 체크포인터는 실행 상태를 저장하고 재개를 지원합니다. 메모리에만 저장하는 구현은 프로세스 재시작 때 사라질 수 있으므로 운영 환경의 영속 저장과 구분해야 합니다. 사람 승인에는 일시정지와 같은 스레드의 재개를 연결합니다. [6] [7]

다만 체크포인트가 **외부 발송의 정확히 한 번 실행**을 자동 보장하지는 않습니다. LangGraph의 interrupt가 있는 노드는 재개할 때 처음부터 다시 실행될 수 있습니다. 승인 노드와 발행 노드를 분리하고, 외부 쓰기에는 중복 방지 키와 실행 결과 대장을 사용해야 합니다. 승인 대기 전에 이메일 발송을 넣으면 재개 과정에서 다시 발송될 위험이 있습니다. [7]

## 5. Jev Engineering: 판단의 질문은 작게, 실행 권한은 별도로

Jev는 TypeSafe의 System One 결정 모델입니다. Choice는 선택지 중 하나, Score는 순서가 있는 기준의 점수, Noul은 명제가 참이라는 모델의 확률을 반환합니다. Choice·Score의 `confidence`는 확률 분포에서 계산된 확신도이며, Noul에는 같은 별도 필드가 없습니다. 이를 “정답률”이나 “안전하게 실행해도 되는 확률”과 동일하게 취급하면 안 됩니다. [8] [9]

마케터는 “이 캠페인을 잘 운영해줘”보다 좁은 질문을 설계해야 합니다. 한국어 문의의 주제를 정해진 유형 중 고르는 질문, 초안이 승인된 타깃에 얼마나 맞는지 평가하는 질문, 지정 자료에 가격 근거가 있는지 확인하는 질문을 분리합니다. 서로 다른 질문은 같은 자료를 보더라도 독립적으로 평가할 수 있으므로, 앞선 답에 의존하는 질문은 코드가 다음 단계의 상태를 구성해야 합니다. [8]

가상 문의 분류에서는 Choice가 `제품 문의`, `콘텐츠 문의`, `기타/판단 보류` 중 후보를 제시할 수 있습니다. 코드가 허용된 내부 검토 큐로 옮기고, LLM은 사람이 읽을 요약을 작성합니다. **분류 결과만으로 고객에게 이메일을 발송하거나 개인정보를 외부로 전달하지 않습니다.**

Jev의 질문 설계는 공급사의 API 형식에 맞춰야 합니다. 다음은 Jev SDK를 호출하는 코드가 아니라, 모델의 결과를 받은 뒤 적용할 **로컬 정책 함수**입니다. 네트워크나 발행 작업은 하지 않으며 Python 표준 라이브러리만 사용합니다.

```python
from math import isfinite


def next_step(decision, confidence, source_ok, action, threshold):
    allowed_decisions = {"product", "content", "other"}
    internal_actions = {"route_internal", "save_draft"}

    if not isinstance(action, str) or action not in internal_actions:
        return "needs_approval"
    if source_ok is not True:
        return "needs_input"
    if not isinstance(decision, str) or decision not in allowed_decisions:
        return "needs_review"
    if not all(
        isinstance(value, (int, float))
        and not isinstance(value, bool)
        and isfinite(value)
        and 0 <= value <= 1
        for value in (confidence, threshold)
    ):
        return "needs_review"
    if decision == "other" or confidence < threshold:
        return "needs_review"
    return "ready_for_internal_step"


# 0.85는 설명용 기준이며 실제 임계값은 별도 평가로 정한다.
assert next_step("product", 0.92, True, "route_internal", 0.85) == \
    "ready_for_internal_step"
assert next_step("product", 0.99, True, "send_email", 0.85) == \
    "needs_approval"
assert next_step("content", 0.99, False, "save_draft", 0.85) == \
    "needs_input"
assert next_step("other", 0.99, True, "route_internal", 0.85) == \
    "needs_review"
```

`ready_for_internal_step`도 처리 완료가 아닙니다. 실제 큐 저장이나 초안 저장이 성공해야 다음 상태로 전환합니다. API 오류·모델 응답 누락은 별도로 잡아서 검토 또는 실패 상태에 보내고, 높은 확신도를 대신 만들어 넣지 않습니다. Noul의 값을 이 함수의 Choice 확신도 자리에 그대로 넣는 방식도 피해야 합니다.

실행 권한은 모델이 결정하지 않습니다. 허용된 작업, 승인 대상 문서 버전, 승인자의 권한을 서버가 다시 확인해야 합니다. 외부 자료가 “위의 규칙을 무시하라”고 말해도 그것은 처리할 데이터이지 운영 지시가 아닙니다. 입력 필터만으로 프롬프트 인젝션 방어가 끝났다고 보지 말고 도구 권한과 승인 경계를 함께 적용합니다.

## 6. 한국어 업무에서 판단 모델을 평가하는 방법

공급사의 벤치마크는 후보를 선택할 근거이지 우리 업무의 정답표가 아닙니다. 기존 규칙이나 LLM 분류를 기준선으로 두고, 한국어 제품명, 줄임말, 오탈자, 복합 문의와 애매한 표현이 포함된 대표 표본을 만듭니다. 민감 정보는 제거하거나 사용 권한을 확인합니다.

분류 유형마다 사람이 합의한 라벨을 만들고, 질문을 다듬는 데이터와 최종 평가 데이터를 분리합니다. 성능을 보고 같은 평가 데이터에 질문을 계속 맞추면 새 문의에서의 오류를 과소평가할 수 있습니다.

자동 처리된 항목 중 정확한 비율과 전체 업무 중 자동 처리되는 비율을 함께 봅니다. 높은 임계값으로 거의 전부 사람에게 보내면 자동 처리의 정확도는 좋아도 업무 부담은 줄지 않을 수 있습니다. 반대로 자동 처리 범위를 넓히면서 중요한 문의를 놓치는 비용도 살펴야 합니다.

확신도 구간별 실제 정답률, 사람에게 넘긴 이유, 처리 지연과 비용을 기록합니다. “모델이 확신한다”와 “우리 표본에서 맞았다”는 별개입니다. 임계값은 질문·오류 비용·한국어 표본에 따라 정하고, 변경한 뒤에는 같은 기준선으로 다시 비교합니다. TypeSafe 공식 문서도 위험도와 실제 도메인 성능에 따라 임계값을 조정하도록 안내합니다. [9]

## 7. 한 콘텐츠 캠페인에 네 요소를 적용해보기

가상 B2B 캠페인에서는 먼저 제품 자료와 타깃·금지 표현을 Harness의 기준으로 고정합니다. 데이터 집계는 코드가 하고, LLM은 메시지 가설과 초안을 만듭니다. 초안의 근거와 형식은 검수가 확인하며 Loop는 실패한 부분만 정해진 한도 안에서 수정합니다.

채널마다 다른 검수가 필요해지면 Graph의 분기를 사용합니다. 블로그는 공개 출처·메타데이터·본문의 일치, 광고 소재는 승인된 주장과 랜딩 메시지의 일치, CRM 초안은 대상군과 수신 조건을 확인합니다. 외부 발행은 사람이 승인한 동일 버전만 실행합니다.

Jev는 그중 범위가 좁고 반복되는 판단에만 후보로 넣습니다. 문의 주제 분류나 정해진 기준의 초안 평가가 예입니다. 가격 계산, 파일의 존재, 입력 필드 검증, API 저장 성공은 모델이 판단할 문제가 아니라 코드와 실제 응답으로 확인할 항목입니다.

발행 이후에는 기술 실행 로그와 마케팅 성과를 분리합니다. 기술 로그의 `run_id`, 노드, 모델·질문·정책 버전, 중단 이유는 운영 진단용입니다. GA4와 Meta의 글 보기·CTA 클릭·문의 저장 성공은 방문자 행동 측정용입니다. **콘텐츠 생성 완료, 페이지 게시 완료, 문의 접수 완료, CRM의 유효 리드는 같은 사건이 아닙니다.** 고객 이메일이나 원문 문의를 분석 이벤트에 넣지 않습니다.

처음에는 외부 발행 없이 기존 담당자의 결과와 나란히 비교하는 방식으로 운영합니다. 승인 대기, 모델 오류, 저장 실패와 중복 요청을 확인한 뒤에야 낮은 위험의 내부 작업부터 자동화 범위를 넓힙니다. 내 캠페인을 문서로 풀어보고 싶다면 [도서의 실무 활용 가이드](/blog/command-marketing-book-practical-guide)와 [콘텐츠·검색 검수 워크시트](/resources/content-search-checklist)를 함께 활용하세요.

## 8. 마케터가 개발팀과 합의할 4주 도입 로드맵

**첫째 주는 업무와 기준선을 정합니다.** 반복되는 한 업무를 선택하고 입력 자료, 사람이 보는 산출물, 오류 비용을 적습니다. 현재의 처리 시간과 수정 횟수를 기록하되 비교 조건을 맞춥니다. 데이터 조회와 외부 쓰기의 권한도 나눕니다.

**둘째 주는 Harness와 제한된 Loop를 만듭니다.** 자료 버전, 도구의 입출력, 검수 규칙, 중단 상태와 재시도 한도를 고정합니다. 성공뿐 아니라 권한 만료·자료 누락·도구 실패를 시험하고 마지막 정상 상태를 복구할 수 있는지 봅니다.

**셋째 주는 필요한 분기만 Graph로 정리합니다.** 사람 승인이나 여러 채널의 검수처럼 실제 경로가 갈라지는 부분을 노드와 상태 계약으로 표현합니다. 기존 직선형 워크플로로 충분한 업무에 그래프를 추가할 필요는 없습니다. 외부 실행의 중복 방지와 승인 버전 일치를 확인합니다.

**넷째 주는 결정 모델을 비교하고 운영 범위를 정합니다.** 충분한 한국어 표본으로 기존 규칙·LLM·Jev를 비교합니다. 자동 처리의 정확도, 검토량, 지연과 전체 비용이 목표에 맞는지를 봅니다. 적합하지 않으면 기존 판단 방식을 유지합니다. 이 4주는 제안하는 진행 순서이며 완료 기간이나 성과 약속이 아닙니다.

운영에 들어가면 모델, SDK, 질문, 기준 자료와 정책의 버전을 함께 기록합니다. 새 모델이 나올 때마다 전체 시스템을 바꾸지 말고 바뀐 부품을 고정 평가셋에서 비교합니다. 검수 실패가 늘거나 API 형식이 달라지면 검토 경로로 전환하고 마지막 정상 설정으로 복구합니다. 모델 단가만이 아니라 재시도, 저장, 검수자의 시간과 잘못된 실행의 비용까지 계산해야 합니다. [3]

## 자주 묻는 질문

### Harness·Loop·Graph·Jev를 모두 도입해야 하나요?

아닙니다. 이 순서는 이해와 도입을 돕는 관점이지 필수 교체 단계가 아닙니다. 운영 규칙과 상태 관리부터 시작하고, 반복·승인·분기가 필요한 업무에 해당 요소를 추가합니다. Jev는 평가 결과가 적합할 때만 좁은 판단에 적용합니다.

### 마케터도 직접 코딩을 해야 하나요?

모든 코드를 작성할 필요는 없습니다. 대신 입력 원본, 산출물, 실패 조건, 승인 대상과 성과 지표를 구체적으로 설명해야 합니다. 실행 권한과 상태 저장을 구현하는 일은 개발팀과 협업할 수 있습니다. 노코드 도구도 같은 검증·권한·재개 조건을 확인해야 합니다.

### Graph와 다중 Agent는 같은 의미인가요?

다릅니다. Graph는 상태와 업무 경로를 표현하는 방식입니다. 하나의 모델과 코드·검수·사람 승인 노드만으로도 구성할 수 있습니다. Agent 수를 늘리는 것보다 각 단계의 입출력과 실패 경로가 명확한지가 중요합니다.

### Jev의 confidence가 높으면 광고나 이메일을 자동 실행해도 되나요?

아닙니다. 확신도는 허가나 실제 정답률이 아닙니다. 업무 데이터로 판단 성능을 평가하고, 예산 변경·외부 발송·공개 발행은 별도 권한과 승인 정책으로 제어해야 합니다. 승인 후 산출물이 바뀌면 같은 승인으로 실행하지 않습니다.

### 어떤 마케팅 업무부터 적용하는 것이 좋나요?

승인된 자료로 만드는 초안, 내부 검토용 문의 주제 분류처럼 범위가 좁고 비교 가능한 업무가 출발점입니다. 첫 단계에서는 외부 실행 없이 담당자의 결과와 비교하고, 자료 누락·도구 오류·저장 실패가 올바르게 중단되는지 확인합니다.

### 2026년 10월 이후 모델이 바뀌면 가이드도 전부 바뀌나요?

모델과 SDK의 명칭·출력 형식·가격은 다시 확인해야 합니다. 입력 기준, 최소 권한, 상태 저장, 검수, 승인과 결과 대조라는 설계 원칙은 특정 모델에 종속시키지 않는 편이 좋습니다. 부품 교체 뒤에는 기존 평가 기준으로 회귀 여부를 확인합니다.
